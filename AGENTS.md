# Правила работы с Unity/C#-проектом

## Контекст и работа

- Перед работой с игровой логикой или архитектурой читать обзор и нужные разделы [Docs/project-map.md](Docs/project-map.md), затем проверять соответствующий код и ассеты. Платформа, масштаб, версия Unity, структура, запуск и планы хранятся в карте, не в этих правилах. Полный аудит выполнять только по запросу или обоснованной необходимости.
- При переносе шаблона в другой проект составить его собственную карту в рамках задачи на настройку; не переносить сведения о прежней игре. Если карты нет, исходить из проверенного кода и требований пользователя.
- При консультации не менять файлы. Запрос на реализацию или согласование конкретного предложения разрешает необходимые правки в пределах задачи; существенное расширение согласовывать отдельно.
- Обновлять карту в той же задаче при изменении описанного поведения, ответственности, конфигурации или точек входа, а также при обнаружении подтверждённых ошибок, устаревших сведений или существенных пробелов. Указывать дату и область проверки; отделять реализацию от планов. Код и ассеты определяют текущее поведение, но не отменяют согласованные требования.
- Обосновывать решения требованиями и последствиями; незнакомые понятия объяснять на примерах проекта. Отличать факты от предположений, аргументировать согласие или возражение, пересматривать выводы при новых данных.
- Если требуется решение пользователя, сразу описывать суть вопроса, конкретное предлагаемое изменение, рекомендацию и существенные последствия; при наличии содержательных альтернатив кратко объяснять выбор. В том же сообщении формулировать прямой вопрос для согласования, чтобы пользователь мог ответить без дополнительного запроса пояснений. Не ограничиваться названием темы или фразой «следующий шаг — обсудить…». Уже согласованные действия выполнять без повторного запроса разрешения.
- Перед созданием модуля определить ответственность, владельца состояния и зависимости; проверить, подходит ли существующий модуль.

## Архитектура

- В собственном игровом коде запрещены статические поля, методы, классы и Singleton-паттерн. Стандартный API Unity/.NET разрешён. Зависимости передавать явно; создание и время жизни сервисов контролирует соответствующий владелец.
- Соблюдать SOLID без формального наращивания классов, интерфейсов и слоёв. Предлагаемое отступление от конкретного принципа объяснить с последствиями и согласовать до реализации.
- **SRP:** объединять логику, меняющуюся по одной причине; разделять независимые обязанности. Несколько связанных действий могут составлять одну ответственность.
- **OCP:** предусматривать расширение для обоснованных ожидаемых изменений. Не строить универсальность без сценария; изменение требований и исправление ошибок допускают правку существующего кода.
- **LSP:** сохранять контракт базового типа, его инварианты и гарантии результата, не усиливать предусловия. Проверка типа сама по себе не доказывает нарушение; оценивать совместимость поведения.
- **ISP:** интерфейсы формировать по связным потребностям потребителей, разделять по разным ролям; не дробить механически до одного метода.
- **DIP:** правила не зависят от деталей ввода, отображения и инфраструктуры; контракты границ выражают потребности правил, детали их реализуют. Интерфейс не обязателен для каждого класса; конкретные типы данных и значений допустимы.
- У состояния один авторитетный источник и ответственный за изменение. Индексы и кеши допустимы с явным обновлением; независимо изменяемые копии состояния — нет.
- Проверки и согласованность состояния обеспечивает его владелец. Самостоятельные алгоритмы можно выделять отдельно с явными зависимостями; использование данных не требует переносить алгоритм к их владельцу.
- Представление отображает состояние и результаты операций; ввод передаёт явные команды. Обязательный порядок изменения состояния определяет игровая логика, независимо от UI и анимаций.

## Код

- Четыре пробела, фигурные скобки на отдельных строках. Типы, методы и свойства — PascalCase, приватные поля — `_camelCase`, интерфейсы — с префиксом `I`. Файл соответствует основному типу. Комментарии на русском, без регионов.
- Поля приватные; необходимое внешнее чтение — через свойства. Изменения с проверками или согласованными действиями — через методы владельца. Публичный setter не должен обходить эти правила.
- `[SerializeField] private` — для требующих сериализации настроек и ссылок. Временное состояние и зависимости инициализации не сериализовать без необходимости; определить основной способ назначения каждой зависимости.
- Неочевидным числам давать имена; параметры баланса хранить в конфигурации, устойчивые значения алгоритма — в константах. Очевидные литералы допустимы. Совпадение чисел не делает разные по смыслу значения одной настройкой.
- Имена отражают назначение, при необходимости — единицы и условия использования. Использовать термины проекта; суффиксы Provider/Handler/Spawner и подобные выбирать по роли, не обязательному шаблону.
- Функция выполняет одну связную задачу; последовательные шаги допустимы. Выделять самостоятельные детали, когда это улучшает понимание, сохраняя видимость условий, порядка и побочных эффектов. Оценивать связность, вложенность и повторение, а не только длину; простые проверки не требуют отдельного метода.
- Данные и зависимости передавать явно. Много параметров — повод проверить ответственность; объединять их только в осмысленные настройки или запросы, не в контейнер несвязанных зависимостей.
- Комментарии объясняют причины, неочевидные правила, ограничения и контракты, не повторяют очевидный код и не компенсируют неточные имена. Обновлять их вместе с поведением и сохранять полезные пояснения при рефакторинге.

## Проверки и сохранность

- Выбирать проверки по поведению и риску: автоматические тесты для правил, Play Mode для взаимодействий Unity, сцен и префабов; при сквозных изменениях — связанные основные сценарии. Тесты размещать в отдельных EditMode/PlayMode assemblies, именовать по сценарию и ожидаемому результату. Сообщать выполненные проверки, результат и ограничения.
- Сохранять чужие локальные изменения. Ассеты переносить и переименовывать вместе с `.meta`, сохраняя GUID; учитывать миграцию сериализованных полей/типов и проверять затронутые ссылки сцен и префабов.
- Коммитить `.meta` вместе с ассетами; исключать генерируемые `Library/`, `Logs/`, `obj/` и проекты IDE. Коммиты называть по изменению; в PR описывать результат, проверки, связанные задачи и при визуальных изменениях прикладывать изображение или видео.
